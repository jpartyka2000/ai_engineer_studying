Azure Container Apps does not let you pick arbitrary CPU and memory values. On the Consumption plan, the total CPU and memory across **all** containers in a container app must add up to one of sixteen allowed combinations.

**The allowed combinations.** The ratio is fixed at **1 vCPU : 2 GiB**, in 0.25 vCPU steps:

| vCPU | Memory |  | vCPU | Memory |
|---|---|---|---|---|
| 0.25 | 0.5 Gi |  | 2.25 | 4.5 Gi |
| 0.5 | 1.0 Gi |  | 2.5 | 5.0 Gi |
| 0.75 | 1.5 Gi |  | 2.75 | 5.5 Gi |
| 1.0 | 2.0 Gi |  | 3.0 | 6.0 Gi |
| 1.25 | 2.5 Gi |  | 3.25 | 6.5 Gi |
| 1.5 | 3.0 Gi |  | 3.5 | 7.0 Gi |
| 1.75 | 3.5 Gi |  | 3.75 | 7.5 Gi |
| 2.0 | 4.0 Gi |  | 4.0 | 8.0 Gi |

**The consequence nobody likes.** You cannot buy memory without buying CPU. An app that needs 6 GiB of RAM but almost no CPU must take 3.0 vCPU to get it, and you are billed for all 3.0 vCPU-seconds. This fixed ratio is the most common reason a memory-heavy workload is uneconomic on Consumption and belongs on a Dedicated **E-series** profile, where the ratio is roughly 1:8.

**The ceiling and a sharper sub-limit.** Consumption tops out at **4 vCPU / 8 GiB** per replica. But apps using the Consumption plan in a **"Consumption only" environment** — the older environment type, as opposed to the default workload-profiles environment — are limited to **2 cores and 4 GiB**. If you need more than 2/4 and are stuck at that limit, the environment type is why.

**It is per app, not per container.** The combination applies to the **sum** across the main container plus any sidecars. Adding a 0.25 vCPU / 0.5 GiB logging sidecar to a 1.0 / 2.0 main container means the app must be provisioned at 1.25 / 2.5. Init containers also declare resources.

**Configuration.** Resources are set per container in the template:

```json
{
  "name": "main",
  "image": "myregistry.azurecr.io/api:abc123",
  "resources": { "cpu": 0.5, "memory": "1Gi" }
}
```

Changing `resources` is a change to the `template` section, so it **creates a new revision**. There is no vertical scaling of a running app — resizing is a redeploy.

**Dedicated profiles change the rules.** On a Dedicated profile you are constrained by the **profile's** total capacity rather than by the Consumption combination table, and you can limit memory and CPU per app within the profile. Because multiple apps share one profile instance, you have to budget the node: a D4 offers 4 vCPU / 16 GiB nominal, but **the runtime reserves some of it**, so plan on meaningfully less being schedulable. Over-committing a profile means replicas that cannot be placed.

**Sizing method that actually works.**

1. Start small — 0.25 or 0.5 vCPU. Over-provisioning is billed directly on Consumption.
2. Load test to a realistic concurrency and watch CPU, memory, and p95 latency together.
3. Prefer **more small replicas** over fewer large ones on Consumption. Scaling granularity is finer, scale-to-zero savings are the same, and you get better failure isolation. The exception is anything with a large per-replica fixed cost — a JVM heap, a loaded model, a warm cache — where fewer, larger replicas amortize that cost better.
4. Watch for the memory-bound case: if you keep raising the combination to get RAM and the CPU goes unused, price a Dedicated E-series profile instead.
5. Remember the 8 GB **image** size limit on Consumption is separate from the 8 GiB **memory** ceiling. Fat images slow cold starts, which matters a lot if you scale to zero.

**Interview framing.** "Consumption locks you to a 1:2 vCPU-to-memory ratio in 0.25-core steps, capped at 4 vCPU and 8 GiB. That is fine for typical web services, but it means memory-heavy workloads over-buy CPU to get RAM — which is exactly when you move to a Dedicated E-series profile at 1:8 and pay per node instead of per replica-second."
