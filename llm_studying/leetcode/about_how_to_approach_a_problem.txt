The difference between candidates who pass and fail is rarely raw algorithm knowledge — it is process. A structured approach makes you look senior even when you are stuck, and it is what interviewers are actually scoring.

**The framework: clarify, plan, code, test, analyze.**

**1. Clarify (1–3 minutes).** Do not start coding. Restate the problem in your own words and confirm you have it right. Then ask about:
- **Input size.** "What's the range of n?" This tells you the target complexity, which often tells you the pattern.
- **Input properties.** Sorted? Duplicates allowed? Negative numbers? Empty input possible?
- **Output.** Return the value or the index? If there are multiple valid answers, any one, or a specific one?
- **Edge cases.** Empty array, single element, all identical elements.
- **Constraints on the approach.** Can I modify the input? Is extra space allowed?

Even when the problem statement answers these, asking one or two shows you think before coding. Two Sum with "can I assume exactly one solution?" is a good question; so is "are the numbers sorted?" — because the answer changes the optimal approach from hash map to two pointers.

**2. Work an example by hand.** Take a small input and solve it manually. This does two things: it catches misunderstandings before you write code, and it very often reveals the pattern. Say what you notice out loud.

**3. State a plan before you type.** Describe the approach in words and give its complexity. It is entirely acceptable — often preferred — to start with brute force:

"The brute force is to check every pair, which is O(n²). I think I can do better: if I store each value I've seen in a hash map as I go, then for each element I can look up its complement in O(1). That's one pass, O(n) time and O(n) space. Shall I code that?"

That paragraph demonstrates problem-solving, optimization, complexity analysis, and communication before a single line of code exists. **Getting buy-in on the plan also protects you** — if the interviewer wanted something else, you find out now rather than after twenty minutes of coding.

**4. Code it, narrating.** Write clean code and say what you are doing. Concretely:
- Use real variable names: `left`, `right`, `seen`, `count` — not `i`, `j`, `x`, `tmp`.
- Handle the edge cases you identified, up front.
- If you need a helper, write the main logic first and stub the helper, then fill it in.
- If you get stuck mid-implementation, say so and think out loud. Silence is the worst option.

**5. Test by tracing, before claiming you're done.** Walk through your code line by line with a small example and track the variable values out loud. Then test:
- the normal case
- the empty input
- a single element
- duplicates, or the target at the boundary

Finding your own bug during a trace is a **positive** signal. Declaring victory on broken code is a strongly negative one.

**6. State the complexity.** Time and space, with the reason. Then mention a trade-off if one exists: "This is O(n) time and O(n) space. If we couldn't use extra space, sorting first would give O(n log n) time and O(1) extra space."

**What to do when you are genuinely stuck.** In order:

1. **Re-read the problem.** You have probably missed a constraint, and constraints are hints.
2. **Try a smaller case.** n=1, n=2, n=3 by hand. Patterns emerge.
3. **Reach for brute force and get it working.** A correct O(n²) beats an unfinished O(n). You can then optimize with time remaining.
4. **Run through the pattern list.** Sorted input → binary search or two pointers. Substring with a property → sliding window. Counting or lookups → hash map. Matching or nesting → stack. Shortest path unweighted → BFS. Top k → heap. All combinations → backtracking. Overlapping subproblems → DP.
5. **Ask for a hint.** Phrase it as progress, not surrender: "I'm considering a sliding window here but I'm not sure how to handle shrinking when there are duplicates — am I on the right track?" Interviewers expect to give hints. Taking one costs far less than going silent.

**Things that hurt you, in rough order of severity.**
- Silence. The interviewer cannot grade thinking they cannot hear.
- Coding immediately, with no plan.
- Insisting your code works when the interviewer is pointing at a bug.
- Ignoring the hint you were just given.
- Not knowing the complexity of your own solution.
- Unreadable code: single-letter names, no structure, deeply nested conditionals.
- Not handling the empty input.

**Things that help you.**
- Restating the problem and asking about input size.
- Naming the pattern explicitly: "this looks like a sliding window problem."
- Brute force first, then optimizing out loud.
- Finding your own bugs by tracing.
- Proactively stating complexity and trade-offs.
- Clean naming and small helper functions.

**Time management for a 45-minute interview.** Roughly: 3–5 minutes clarifying and planning, 15–20 coding, 5–8 testing and debugging, 2–3 on complexity and follow-ups. If you are 25 minutes in with nothing written, switch to brute force immediately — an unfinished elegant solution scores far below a finished inelegant one.

**One last framing.** The interviewer is trying to answer "would I want this person debugging a production issue with me at 2am?" They are evaluating how you think and communicate under mild pressure, using an algorithm problem as the instrument. Optimal code delivered in silence answers the algorithm question but not theirs.
