LeetCode is the standard practice platform for software engineering coding interviews. This topic covers **Easy and Medium** problems using **core data structures and algorithms only** — the material that actually appears in interviews at the overwhelming majority of companies.

**The scope of this topic, stated precisely.**

In scope:
- Arrays, strings, hash maps and hash sets
- Two pointers, sliding window, prefix sums
- Binary search (on arrays, and on the answer)
- Linked lists
- Stacks (including monotonic stacks), queues, deques
- Binary trees and binary search trees — traversals, DFS, BFS
- Heaps / priority queues
- Graphs — BFS, DFS, topological sort, and basic union-find
- Backtracking — subsets, permutations, combinations
- Dynamic programming — 1-D and simple 2-D
- Greedy and interval problems
- Sorting fundamentals and bit manipulation
- Big-O analysis

**Deliberately out of scope**, because it is not what Easy/Medium interviews test:
- Self-balancing trees — **AVL trees, red-black trees**
- **B-trees** and B+ trees (database internals, not interview coding)
- Segment trees, Fenwick trees / binary indexed trees
- Suffix arrays, suffix automata, Aho-Corasick
- Network flow, min-cut, bipartite matching
- Heavy-light decomposition, link-cut trees
- Advanced string matching like KMP or Rabin-Karp

Two notes on that boundary. First, you are never asked to *implement* a red-black tree in a coding interview — you may be asked what a balanced BST gives you (O(log n) operations), which is a concept, not an implementation. Second, **tries** sit just outside this scope: they appear in a handful of Mediums and are not obscure, so they are worth learning eventually, just not before the patterns above are solid.

**Easy vs Medium, honestly.**

**Easy** problems test whether you know the data structures and can write correct code. One idea, direct implementation, usually under 20 lines. Typical: Two Sum, Valid Parentheses, Merge Two Sorted Lists, Best Time to Buy and Sell Stock, Invert Binary Tree, Contains Duplicate.

**Medium** problems test whether you can **recognize a pattern** and combine two ideas. This is where real interviews live — the large majority of interview questions at most companies are Medium-difficulty. Typical: Longest Substring Without Repeating Characters, Group Anagrams, Number of Islands, Course Schedule, Coin Change, LRU Cache, Validate BST.

The jump from Easy to Medium is not about harder code. It is about the step where you look at a problem and think "sorted array, looking for a pair — that's two pointers" instead of reaching for nested loops. That recognition step is the skill this topic is built around.

**How the patterns map to problems.** Roughly, a Medium problem is solvable once you identify which of about a dozen patterns applies:

| Signal in the problem | Pattern |
|---|---|
| "find a pair/triplet", array is sorted | two pointers |
| "longest/shortest substring or subarray with property X" | sliding window |
| "count/lookup seen values", "anagram", "duplicate" | hash map or set |
| sorted input, or "find the minimum X that works" | binary search |
| "matching", "nesting", "next greater element" | stack |
| "level by level", "shortest path in unweighted graph" | BFS |
| "all paths", "connected region", "explore fully" | DFS |
| "top k", "k largest/smallest", "median of stream" | heap |
| "all combinations/permutations/subsets" | backtracking |
| "count the ways", "min/max over choices", overlapping subproblems | DP |
| "intervals", "merge", "schedule" | sort then greedy sweep |
| "prerequisites", "ordering", "cycle" | topological sort |

**How to practice, in order of what matters.**

1. **Learn the pattern, not the problem.** Doing 500 problems without organizing them by pattern is worse than doing 150 organized by pattern. You are building a lookup table from problem signals to techniques.
2. **Time-box.** Give a Medium 25–35 minutes. If you are stuck with no progress, read the solution, understand it, then **re-implement it from scratch the next day without looking**. Struggling for three hours teaches less than a focused attempt plus deliberate review.
3. **Write code that compiles in your head.** In a real interview you often have no autocomplete and no test runner. Practice writing a full solution before running anything.
4. **Say the complexity out loud** for every problem, time and space, before you look at the answer. Interviewers ask this every single time.
5. **Revisit.** Spaced repetition on problems you got wrong beats new problems. Keep a list of the ones that beat you.
6. **Simulate the real thing.** Talk through your approach aloud before coding. Silence while you think reads very differently from a narrated thought process.

**What interviewers are actually grading.** Not just "did it pass." Roughly: problem-solving approach and whether you asked clarifying questions; whether you stated a plan before coding; code correctness and readability; whether you identified and handled edge cases; whether you can state and justify complexity; and communication throughout. A working brute force that you correctly analyze and then optimize out loud usually beats a memorized optimal solution delivered in silence.

**A realistic study sequence.** Arrays and hashing → two pointers → sliding window → binary search → linked lists → stacks and queues → trees (traversals, then BST) → heaps → graphs (BFS/DFS, then topological sort) → backtracking → 1-D DP → 2-D DP → greedy and intervals → bit manipulation. Each builds on the previous; DP last, because it is the pattern that most benefits from having recursion and memoization already comfortable.
