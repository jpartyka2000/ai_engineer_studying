SGLang has become a standard inference backend inside reinforcement learning training stacks (RLHF, RLVR, GRPO-style pipelines). Understanding why makes for a strong answer about the training/inference boundary.

**Where inference sits in RL post-training.** The loop for policy-gradient-style LLM training is:

1. **Rollout / generation** — the current policy generates completions for a batch of prompts. This is *inference*, and it is usually the dominant cost of the iteration (often well over half the wall clock).
2. **Scoring** — a reward model, verifier, test suite, or rule set scores those completions.
3. **Policy update** — compute advantages and take a gradient step on the policy weights.
4. **Repeat** — with the *updated* weights.

Step 1 is exactly what a serving engine is good at, and step 4 is what makes it awkward: the weights change every iteration, so you cannot just stand up a static server.

**What an RL framework needs from an inference engine.**

- **High-throughput batch generation.** Thousands of rollouts per iteration, latency mostly irrelevant, throughput everything. Continuous batching plus a large KV pool is precisely right.
- **In-process embedding.** Running a separate HTTP server and paying serialization on every rollout is wasteful. SGLang's offline `Engine` runs in the trainer's own process.
- **Fast weight updates without a restart.** After each policy step, the engine must pick up new weights. Restarting means re-loading weights, re-capturing CUDA graphs, and re-warming — unacceptable per-iteration. SGLang exposes weight-update paths (`/update_weights_from_disk` and in-process equivalents, plus checkpoint-engine integration) that swap weights in place while keeping the process, graphs, and memory pools alive.
- **Memory sharing / offload coordination.** The trainer needs GPU memory for optimizer states and activations; the rollout engine needs it for weights and KV cache. They cannot both have it at once. Frameworks either colocate with explicit memory handoff (release the KV pool during the training step, reacquire for rollout) or place rollout and training on separate GPU pools.
- **Prefix caching.** RL rollouts are unusually prefix-heavy: the same prompt is typically sampled *n* times for group-relative advantage estimation (GRPO samples a group per prompt). All n samples share the entire prompt, so RadixAttention computes that prefill once instead of n times. For a long prompt and n=8 or 16, this is a very large saving and a genuinely good example to cite for why cross-request prefix caching matters.
- **Deterministic / reproducible modes.** For debugging training instability, being able to reproduce a rollout bit-for-bit is valuable, which is what SGLang's deterministic inference mode is for.

**The stale-weights subtlety.** For strict on-policy algorithms, rollouts must come from the current policy. But if you overlap generation with training to keep GPUs busy, some rollouts are generated by slightly stale weights, making the update off-policy to a degree. Frameworks handle this with importance-sampling corrections or by bounding staleness to a fixed number of steps. The engineering tension — pipeline for utilization vs. stay on-policy for correctness — is a good thing to name.

**Why this matters for the KV cache specifically.** After a weight update, *every cached KV entry is invalid*: KV is a function of the weights, not just the tokens. So a weight swap must flush the radix cache (`/flush_cache`). This means the prefix-caching win is realized *within* an iteration (across the n samples of each prompt, and across prompts sharing a system prompt), not across iterations. Candidates who claim rollout caching persists across policy updates have missed this.

**Interview framing.** "RL post-training is mostly inference, so the rollout engine is the thing to optimize. SGLang fits because it embeds in-process, does continuous batching for throughput, and — crucially — supports in-place weight updates so you don't restart the engine every policy step. Its prefix caching is a natural fit for group sampling, where n completions share one prompt. The catch is that a weight update invalidates the whole KV cache, so that win is intra-iteration only."
